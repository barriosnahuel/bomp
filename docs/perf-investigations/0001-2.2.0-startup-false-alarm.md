# 0001 — the 2.2.0 "startup regression" was a sampling artifact

- **Date:** 2026-06 · **Trigger:** weekly Bomp performance report · **Verdict:** false alarm, no fix
- **Method:** `/perf-report-triage` skill · **Raw data (private):** `../push-me-backlog/performance-investigations/` (full-fidelity counterpart for this incident)

## Alarm

The weekly report flagged 2.2.0 (code 7) vs 2.1.0 (code 6):

- Cold start ≈645 ms vs ≈157 ms — "4× slower".
- LandingActivity frozen-frame ratio 0.113 vs ≈0 — "new stutter".
- LandingActivity slow-frame ratio roughly flat.

(The report says 2.1.0 ≈157 ms; the segmented BQ pull below gives a 129 ms raw mean for the same
version — the report uses a different window/aggregation than the 60-day BQ export. The conclusion holds
either way. Frame ratios come from the `_st_LandingActivity` screen trace, which spans the **whole
activity** — every bottom-nav tab, not just the Home tab — so read them as activity-wide, not Home-only.)

## What it actually was

A raw **mean over ~24 cold-start samples / ~52 screen traces** per version (60-day retention). Both
"regressions" are driven **almost entirely by one low-tier device** having a pathological ~2-day window
**immediately after the 2.2.0 rollout**.

### Cold start, after segmenting by device

| version | n | raw mean | **mean excl. the one outlier device** |
|---|---|---|---|
| 2.1.0 | 26 | 129 ms | 129 ms |
| 2.2.0 | 24 | **645 ms** | **155 ms** |

- The reported 645 ms **is** the raw mean, and it is **entirely** ~9 cold starts (≈1.0–1.9 s) from a
  single low-tier device over 2 days. Excluded → 155 ms ≈ 2.1.0's 129 ms.
- **Same-model across versions (the decisive check):** flagship-tier flat (~56→~59 ms); a slow device
  that had been the worst on 2.1.0 (~573 ms) **improved to ~265 ms on 2.2.0** — consistent with 2.2.0's
  newly-shipped Baseline Profile working.

### Frozen / slow frames, same story

| version | n | raw frozen | **frozen excl. outlier** | raw slow | **slow excl. outlier** |
|---|---|---|---|---|---|
| 2.1.0 | 67 | 0.012 | 0.012 | 0.283 | 0.283 |
| 2.2.0 | 52 | **0.113** | **0.030** | 0.382 | **0.286** |

- 0.113 collapses to 0.030 without the one device; slow frames excl. the outlier are identical.
- 2.1.0 was **not** truly 0 — a slow device hit 0.4. The residual 2.2.0 frozen comes from a loaded slow
  device that janks on the entry activity in **both** versions. Within small-sample noise.

### Most likely cause of the outlier

Single device, tight post-rollout window ⇒ **install-time behaviour** (ART interpreted/JIT before Play
AOT-compiles the shipped Baseline Profile). Expected, transient, self-healing — and exactly what the
Baseline Profile mitigates over time.

## Code cross-check (static, on `develop`)

Suspected main-thread causes were checked against the code and largely cleared:

- A synchronous `Settings.Global.getFloat(ANIMATOR_DURATION_SCALE)` does run on the main thread in the
  home swipe-hint effect (`ui/home/SoundItem.kt`), but it is **guarded + one-shot** (welcome hint only)
  — hygiene, not systemic jank. Optional cleanup: move off-main.
- The home-list sort + `String.lowercase()` runs on `Dispatchers.IO` and is sub-ms for ≤200 items — **not**
  a jank source.
- The recorder draft flow is `.flowOn(Dispatchers.IO)` (`file.exists()` off-main) — **not** a jank source.

## Outcome / follow-ups

- **No startup/frame fix warranted.** The premise dissolved at the de-confounding step; `develop` (2.3.0)
  has no carried-forward regression on this axis.
- **Worth doing anyway:** regenerate the Baseline Profile before the 2.3.0 release (release-checklist item;
  `CONTRIBUTING.md` § *Baseline Profile*) — the committed profile predates the recorder + several dep bumps.
- **Process fix:** the weekly report should prefer a **median / per-device view** over a raw mean across
  ~24 samples; that raw mean is what manufactured this alarm.
